# Telegram 渠道与工具执行边界

> 工作区内 `.env` 凭据的保密承诺已由 [ADR 0016](0016-local-trust-for-workspace-credentials.md) 替代：允许本地信任模式，工具可读取工作区凭据。

Jarvis 以 `Application` / `Agent` 为运行内核，首个非 CLI 渠道采用 Windows 上本机常驻的 Telegram Bot long polling；渠道层负责身份校验、消息去重与排队、会话映射及结果发送，不把 Telegram 消息格式写入 Agent。CLI 保留。选择先做单用户、单渠道而非通用多渠道平台，避免在运行内核之外引入多用户权限和状态来源；本决定延续 ADR 0007、0008、0013 的事件事实源、副作用未知不重放及应用生命周期契约。

启动工作区取进程启动时的当前目录，运行期间固定；相对路径按当前启动工作区解释。保持现有 `SessionStore` 按工作区目录存放、列出和恢复会话的行为，不迁移为全局会话：Telegram 私聊只映射到**当前工作区内**可持久恢复的会话；换目录启动进入新工作区的会话集合，不自动沿用原目录的历史，返回原目录启动才能恢复其会话。仅接受配置中的一个 Telegram 数字用户 ID 的私聊；Token 与用户身份不同，均不得进入消息日志、会话或模型上下文。首版只收发文本；群聊、文件传输、权限模式切换和后台定时任务不在范围内。

模型对外的工具统一为 `read`、`write`、`edit`、`bash`；移除 `list_directory` 及模型可见的 `tool_search`，不为了此次渠道改造删除内部运行时可能需要的历史工具定义。废除三档权限模式，改为执行边界：工作区内 `read/write/edit` 自动执行，现有 Windows 沙箱内 `bash` 自动执行；工作区外 `read` 默认拒绝。其他越界或无法安全执行的操作先阻止，只有能在执行前明确展示并限制范围的**具体操作**才可请求单次批准；批准不能代替实际的操作系统隔离，也不赋予后续操作通行权。无法可靠限制的越界 `bash` 拒绝执行，不降级为普通用户权限。任何来自文件或工具结果的文字都不能充当授权。

收到任务先反馈，完成后通知；同一私聊任务串行、后续普通消息排队，`/cancel` 优先请求取消，不能撤销已发生的副作用。按 Telegram 消息身份去重；重启后不自动重跑未完成任务或工具，向用户报告状态未知。确认请求在任务结束、取消、超时或重启时失效，旧按钮不能批准新操作。

**实现验收门槛**：相对于制定本决策时的基线，`ROOT_DIR` 覆盖启动目录、越界 `read`、尚无独立 `write`、额外模型工具和三档权限都需要在实现时改造并通过回归；不能把 ADR 当成已实现保证。Windows AppContainer 对工作区内外文件、进程树、网络和重解析点的限制需实测；尤其不能靠解析任意 PowerShell 文本预测副作用。检查后使用的竞争条件及非 loopback 网络能力不能因为有限探针通过就视为已证明安全。Telegram Token 的配置来源必须在工作区外（或环境变量），工作区内的 `.env` 不得通过文件工具或沙箱命令泄漏。外部操作的单次授权在可靠执行路径完成前保持拒绝，不能用按钮假装已提供越界能力。执行层及会话事件应记录拒绝、授权和未知状态，但绝不记录 Bot Token。具体任务拆分与验收案例见 GitHub Issue #45–#49。
